# Coverage: Script and Oracle

This file holds the per-operation coverage detail for `Script`, worked Script properties, corpus conversion, and `dogelib-oracle`.
See [COVERAGE.md](../../COVERAGE.md#operations) for the compact matrix and [COVERAGE.md](../../COVERAGE.md#legend) for field meanings and theorem tags.
See [docs/soundness/script.md](../soundness/script.md), [docs/soundness/cryptography.md](../soundness/cryptography.md#secp256k1-public-key-parser-and-cores-verifier), and [docs/soundness/oracle-and-harness.md](../soundness/oracle-and-harness.md) for theorem hypotheses and boundaries.
See [docs/comparison-evidence.md](../comparison-evidence.md) for finite Core comparison counts and streams.

## Oracle, `dogelib-oracle`

- **Definition**: `Exports.respond` and the operations in `Serialization.Exports.Oracle`, `Transaction.Exports.Oracle`, `Work.Exports.Oracle`, `Block.Exports.Oracle`, `Block.Exports.Validate`, `Cryptography.Exports.Oracle` and `Script.Exports.Oracle`, format `dogelib-oracle/1` ([docs/oracle.md](../oracle.md))
- **Theorems**: None: an IO adapter, outside the specification (SOUNDNESS.md, B4)
- **Comparison**: `bash scripts/test_oracle.sh`: 320 fixtures with expected values from Core's files and source and `hashlib`. All 500 records of Core's `sighash.json` (D26) through `sighash.legacy`. The 91 + 68 base-mode records of `tx_valid.json` and `tx_invalid.json` (D28, D29) through `tx.decode_base`: bytes back and the ID. Answers line by line while its input stays open. `scripts/test_oracle.sh` does not run Core. `scripts/compare_core.py` runs Core at `e0a1c15` on the same requests ([docs/core-harness.md](../core-harness.md#the-core-harness)). Both witness operations also check all 198 corpus records, including stacks and both hashes. The comparison sends 389,785 stream requests and fails if the count of any operation differs from its table ([counts](../comparison-evidence.md#the-comparison)). It excludes unsupported Script results and checked harness refusals from verdict agreement. Twelve stream requests are checked harness refusals. Supported results have no disagreements. The work sets cover compact arithmetic, retarget arithmetic and next-work selection. Typed view errors have oracle fixtures and stay outside the Core comparison. The `large structured base` set adds 984 requests through both base operations and the legacy transaction argument. It covers counts of 253, 254 and 1000, larger scripts, malformed fields, truncations and trailing bytes. Hash and block sets compare committed fixtures, every proper header prefix, raw field boundaries, Merkle subtree duplications and hash padding boundaries. See their operation rows and [the comparison sets](../comparison-evidence.md#the-comparison). The legacy corpus streams compare all 925 inside-milestone records with each checker: each checker gives 925 agreements. The 2,000 legacy mutations per checker use seed `20261106`. Base gives 1,956 compared verdicts and 44 unsupported flags. Transaction also gives 1,956 compared verdicts and 44 unsupported flags. All these streams have zero disagreements.
- **Refinement**: The base operations and legacy transaction argument use the slice readers. `Transaction.abstractRead_readBaseSlice` and `Transaction.decodeBaseCompleteSlice_eq` connect them to the list specification. The JSON adapter has no refinement theorem. Witness operations use list readers.
- **Excluded**: Building a transaction from fields. Its request errors, which the comparison with Core does not test

## Script evaluation, one `EvalScript` call

- **Definition**: `Script.evalScript`, `evalLoop`, `evalInstruction`, `execOpcode`, `checkSigStep`, `checkMultisigStep`, `multisigCheck`, `checkLockTimeStep`, `checkSequenceStep`, `EvalResult`, `Unsupported` in `Script.Eval`. `Script.ScriptError` in `Script.Error`. `Script.supportedFlags` and the flag bits in `Script.Flags`
- **Theorems**: `evalScript_unsupportedFlags`: a flag outside the seven of design record 0003 gives `unsupported` first. `evalScript_scriptSize`. `evalScript_ok`: a success ends at the end of the script with an empty `vfExec` and satisfies `ExecState.WellFormed`. A nonempty script also leaves the stacks within the combined item limit. `evalScript_flags_congr`: `P2SH` never changes a result. `evalLoop_atEnd`: an unbalanced conditional is rejected. `evalInstruction_pushSize`, `evalInstruction_opCount`, `evalInstruction_disabled`, `evalInstruction_verif`: Core's check order, also in a skipped branch. `evalInstruction_skipped`: a skipped instruction only counts. `evalInstruction_wellFormed`: each successful step keeps the invariants and the stack limit. `execOpcode_*`: the stack effect and underflow error of each implemented opcode, and each unsupported case. `execOpcode_checker_congr`: every opcode outside `0xac` to `0xaf`, `0xb1` and `0xb2` ignores the checker and the script. `execOpcode_script_congr`: every opcode outside `0xac` to `0xaf` ignores the script. `execOpcode_nop2`, `execOpcode_nop3`: CLTV and CSV with their flags clear are NOPs. `execOpcode_cltv_*`, `execOpcode_csv_*`: with a checker, the errors in Core's order, the checker call on a nonnegative operand, and `execOpcode_csv_disabled`: an operand with bit 31 set is a NOP for every checker. Neither opcode pops. `checkSigStep_*`: the `OP_CHECKSIG` checks in Core's order, one checker request with the script code from the separator cursor minus the signature push, and the stack effect. `checkMultisigStep_*`: each `OP_CHECKMULTISIG` error in Core's order, the opcode count raised by the key count, the dummy with and without `NULLDUMMY`, and `checkMultisigStep_matching`: with total checker answers and no encoding error, success exactly when the signatures pair in order with a subsequence of the keys, also in push order. `evalInstruction_signature_skipped`: a skipped signature opcode only counts. One effect theorem for each numeric and hash opcode, from `execOpcode_1add` to `execOpcode_hash256`. `execOpcode_numeric_underflow`, `execOpcode_hash_underflow`, `execOpcode_numeric_decode`: too few items give `INVALID_STACK_OPERATION`, and a failed operand decode gives `UNKNOWN_ERROR`. `execOpcode_addSub_length`: `OP_1ADD`, `OP_1SUB`, `OP_ADD` and `OP_SUB` push at most five bytes. `numericOperand_*`: Core's `CScriptNum` operator asserts hold and no `int64_t` operation overflows on four-byte operands. Termination by construction, without fuel
- **Comparison**: `lake test`: the 1,193 records of `script_tests.json` (D45) run through `verifyScript`. *Script verification* gives the counts. 140 hand cases and 46 underflow cases written from D3 and D24, run without a checker and again with `baseChecker`, except the cases that are unsupported without a checker. The digests of the hash cases come from D45. The hand cases cover the limits at 201 operations, 520-byte pushes, 1,000 items and 10,000-byte scripts. They also cover short pushes, unbalanced conditionals, disabled and reserved opcodes in skipped branches, negative zero and `OP_PICK` operands. For the numeric opcodes they cover operand order, five-byte results, negative zero and non-minimal operands, `OP_NUMEQUALVERIFY` failure and the bounds of `OP_WITHIN`. 48 signature-opcode cases use a lookup-table test checker. They cover each signature-opcode error in Core's order, 0-of-0, 1-of-1 and 2-of-3 matching, early exit and the dummy. They also cover 21 keys, the opcode count from keys, code separators, signature pushes in the script code and the order-dependent encoding check. 6 cases cover `transactionChecker` and `baseChecker`. These known answers do not execute Core. The oracle's default `script.eval` uses no checker. Separate base-checker streams compare 2,386 corpus calls (1,862 compared, 524 unsupported), 49 resource boundaries (48 compared, 1 unsupported) and 2,000 generated calls (all compared), with zero disagreements. `scripts/compare_core.py`: 2,386 individual corpus calls (1,696 compared, 690 unsupported), 49 boundary calls (44 compared, 5 unsupported), and 2,000 calls under seed 20261105 (2,000 compared, none unsupported). The 1,193 two-call compositions give 764 compared results and 429 unsupported results. Supported results have no disagreements with pinned Core. Unsupported reasons and Core outcomes are reported separately. These compositions do not run `VerifyScript` and ignore each record's witness. The `lake test` count treats all 103 witness records as unsupported. The comparator runs their base scripts. Six witness records yield supported results (source_index 1004, 1005, 1101, 1102, 1103, 1104), as do the 13 P2SH records. Thus 764 base compositions compare in this comparison, which runs without a checker. `lake test` runs `verifyScript` with `transactionChecker` and `coreVerifier`: 925 records agree with Core's expected result, 563 acceptances and 362 rejections, and 268 are unsupported.
- **Refinement**: None
- **Excluded**: Signature verification itself, which is the parameter `verify`. `NULLFAIL`. CLTV and CSV with their flags and without a checker. Every flag outside the seven. A caller's stack of 2^31 items or more, where Core's `(int)stack.size()` differs. A caller's item of more than `UINT_MAX` bytes, where Core's `CastToBool` loop can repeat without end.

## Script execution state

- **Theorems**: `init_wellFormed`: the start of every `EvalScript` call satisfies the invariants, for every script and caller stack. `handOff_eq_iff`: two states hand off the same start state exactly when their main stacks are equal. `handOff_wellFormed`, `WithinStackLimit.handOff`. `WellFormed.advance`: moving the cursor past an instruction that `readInstruction` reads keeps the invariants. `WellFormed.markSeparator`: so does setting the separator cursor to the cursor
- **Comparison**: `lake test`: one state with nonempty locals and the raw stack `[[], [0x80], [0, 0]]`. Its `init` and `handOff` keep that stack and reset every other part
- **Refinement**: None
- **Excluded**: P2SH stack copy and restore. *Script evaluation* proves that each opcode step keeps the invariants

## Script instruction reader

- **Definition**: `Script.readInstruction`, `Instruction`, `ReadResult`, `ShortPart`, `IsBoundary` in `Script.Instruction`, defined through `Transaction.readOp`
- **Theorems**: `readInstruction_eq_instruction_iff`: sound and complete against `InstructionEncoding`, for every script and cursor. `readInstruction_eq_instruction_iff_readOp`, `readInstruction_eq_fail_iff_readOp`: agreement with `readOp`. `readInstruction_consumes`: when `readInstruction` reads an instruction, the next cursor lies after the start cursor and at most at the end of the script. The bytes from the start cursor are the bytes of the instruction, then the bytes from the next cursor. `readInstruction_nonpush`: an instruction that `readInstruction` reads with an opcode above `0x4e` is that one byte, pushes nothing and moves the cursor by one. `readInstruction_atEnd_iff`, `readInstruction_truncated_iff`: each failure and the cursor that `GetOp2` leaves. `IsBoundary.not_inside`: no boundary lies inside an instruction that starts at a boundary
- **Comparison**: `lake test`: 50 single reads and 8 loops with hand-derived results. 15 cases come from 14 records of `script_tests.json` at the pin (lines 23 to 34, 442, 538, 721 to 723), and the others from `GetOp2`. They cover `OP_0`, direct pushes, all PUSHDATA forms, every short length field and short data of each push kind. Other cases cover lengths with a nonzero high byte and nonminimal pushes. They also cover separator bytes inside pushed data and reads after cursor 0. `scripts/compare_core.py`: 1,233 `script.read_op` requests against pinned Core. 1,227 are generated reader requests, with every opcode, truncated length fields, truncated payloads and arbitrary cursors. The other 6 are the reader requests of the oracle fixtures. All agree.
- **Refinement**: None
- **Excluded**: Core returns `OP_INVALIDOPCODE` and an empty vector on failure. `truncated` also reports the opcode byte and the short part. Scripts of 2^32 bytes or more have no Core counterpart. The correspondence with `GetOp2` covers scripts of fewer than 2^31 bytes, because a `CScript` iterator difference is an `int32_t`

## Script numbers, `CScriptNum`

- **Definition**: `Script.ScriptNum.decode`, `encode`, `value`, `isMinimal`, `getint`, `DecodeError`, `Script.defaultMaxNumSize` in `Script.Number`
- **Theorems**: For every input: `value_encode`, the value of every encoding is the integer. `isMinimal_iff_encode_value`: Core's minimality test accepts exactly the encodings. `encode_length_le_iff`: at most `k` bytes exactly when `2 * n.natAbs < 256 ^ k`. Every decode result comes from `decode_eq_ok_iff`, `decode_eq_overflow_iff` or `decode_eq_nonMinimal_iff`, with the size check first. `decode_encode`: the round trip within the size. `decode_int64`: decodes of up to 8 bytes fit `int64_t`. `getint_eq_max_min`: `getint` is the clamp to `[-2^31, 2^31 - 1]`, and `getint_decode_default` shows it never changes a default-size decode
- **Comparison**: `lake test`: 21 hand-derived encodings, each decoded at sizes 4 and 5 with and without the requirement. 24 hand-derived decodes: negative zero, non-minimal zeros, Core's `0xff00` exception, overflow before the minimality check, five-byte values. 9 `getint` saturation cases. The 247 integers of the `creation` test of `scriptnum_tests.cpp` (D44), with the round trip within ±(2^31 − 1) and overflow outside it. Core itself does not run
- **Refinement**: None
- **Excluded**: Sizes above 8, where Core's `set_vch` is undefined, and `-2^63`, where `serialize` is undefined. `OP_PICK`, `OP_ROLL` and the numeric opcodes map a decode failure to `SCRIPT_ERR_UNKNOWN_ERROR` (*Script evaluation*)

## Script pattern removal, `FindAndDelete`

- **Definition**: `Transaction.findAndDelete`, `findAndDeleteLoop`, `dropMatches` in `Transaction.LegacySighashReference`, re-exported by `Script.SignatureCode`
- **Theorems**: `findAndDelete_length_le`: never longer. `findAndDelete_separator`: separator removal on fully parsed scripts. `legacyPlans_differ_shortPush`: on `4c 05 aa`, deletion keeps the whole short push, where `scriptCodeBytes` writes `03 4c 05`. `Script.findAndDelete_traversal`: exact traversal of retained instructions and the failed-read suffix, with the count, for every pattern and input. `dropMatches_decomposition`, `dropMatches_exhausted`: exact removed prefix and no match at the cursor after leading deletion. `findAndDelete_empty`, `findAndDeleteLoop_malformed`: empty pattern and complete failed-read suffix. `findAndDelete_scanOps`: a fully parsed script stays fully parsed, when the pattern parses or is longer than the script
- **Comparison**: `lake test`: all 16 `script_FindAndDelete` cases from D46, 8 additional malformed suffix cases from D24. Nine D24 cases cover empty patterns, no match, separator instructions and pushed separator bytes, repeated three-byte copies and short pushes
- **Refinement**: None
- **Excluded**: Visited boundaries can differ from original boundaries. One pass can create a match across retained pieces. Core counts with an `int`, here a `Nat`. Counts above `INT_MAX` are outside the Core compatibility claim

- **Theorems**: `transactionChecker_invalidKey`, `transactionChecker_emptySig`: an invalid key or an empty signature gives `false` for every verifier. `transactionChecker_verify`: otherwise the result is `verify` on the signature without its last byte, the key and `legacySignatureHash` with that byte zero-extended. `transactionChecker_verify_congr`: no other request reaches the verifier. `transactionChecker_checkSig_fixed`: for a request with `ReachesFixedDigest`, a valid key and a script code below 2^64 bytes, the result is `verify` on the signature without its last byte, the key and `legacyOne`. `transactionChecker_checkSig_fixed_congr`: two such requests give the same answer for any transactions, input indices and script codes. `baseChecker_checkSig`. `greedyMatch_iff`: Core's greedy loop succeeds exactly when an ordered match exists. `greedyMatch_eq_noExit`: the early exit does not change the result. `multisigLoop_ok`: with total checks, `multisigLoop` is the greedy loop. `orderedMatch_reverse`. `transactionChecker_checkLockTime`, `transactionChecker_checkSequence`: for an input in range, Core's two checks on its sequence. `transactionChecker_checkLockTime_none`, `transactionChecker_checkSequence_none`: `none` for an index outside the inputs. `lockTimeSatisfied_iff`, `sequenceSatisfied_iff`: Core's conditions with the constants written out. `baseChecker_checkLockTime`, `baseChecker_checkSequence`

The two `lake test` corpus runners and the oracle's `transaction` checker use `coreVerifier` (*Script signature verifier*).

## Script signature verifier, `CPubKey::Verify`

- **Definition**: `Script.coreVerifier`, `coreVerify`, `normalizeS` in `Script.CoreVerifier`
- **Theorems**: `coreVerifier_some`: always `some`. `coreVerifier_invalidKey`, `coreVerifier_badPoint`, `coreVerifier_emptySig`, `coreVerifier_badDer`: steps 1 to 4 of `CPubKey::Verify` give `some false`. `coreVerifier_eq_verify`: otherwise `Ecdsa.verify` on the parsed point, the digest, R and the normalized S. `parseDerLax_lt`: the lax parser stores scalars below `n`. `normalizeS_le_half`, `normalizeS_lt`, `normalizeS_sub`: for `s ≤ n`, normalization gives at most half the order and zero only for `0` and `n`. The result is the same for `s` and `n − s`. `coreVerifier_normalize`: signatures that parse to `(r, s)` and `(r, n − s)` give the same result. `coreVerify_valid`: the scalars and the point satisfy the guards of `Ecdsa.verify_of_valid` exactly when R and S are not zero. `hashToInt_legacyOne`: the digest one gives `e = 2^248`. `transactionChecker_coreVerifier_some`: every `checkSig` request with a script code shorter than 2^64 bytes answers `some`. `multisigRecovery_sound_coreVerifier`: under `MultisigRecoverySpend`, an accepted spend with `coreVerifier` takes the ordinary or the recovery branch. It needs no verifier hypothesis
- **Comparison**: `lake test`: Core's 925 inside-milestone `script_tests.json` records and the 159 eligible transaction inputs run with `coreVerifier` (*Script verification*). The same signature with a high S accepted, and with R equal to `n` or a 33-byte S rejected. One case for each of steps 1 to 4. Expected results come from Core's corpora and from a reading of D50, D52 and D60. `scripts/compare_core.py`: 598 dedicated `pubkey.verify` inputs agree with Core. These include 464 Wycheproof bitcoin cases, 6 Core-signature and reversed-digest cases, 20 parser boundaries, 36 infinity cases and 72 x-above-order cases, including 24 changed-S rejections. - **Excluded**: A 32-bit build of Core, which can differ on a signature of at least 2^24 bytes. That `Point.mulAdd` and `Fn.inv` compute Core's `secp256k1_ecmult` and scalar inverse (SOUNDNESS.md). Witness and Schnorr verification

## Script worked property, fixed digest of `SIGHASH_SINGLE`

- **Definition**: `Script.fixedDigestChecker`, `HasSingleHashType`, `pushScript`, `p2pkhScriptPubKey`, `multisigScript` in `Script.Proofs.FixedDigest`. `SignatureChecker.Extends`, `EvalResult.Decided`, `VerifyResult.Decided` in `Script.Proofs.CheckerExtension`. `Transaction.ReachesFixedDigest` in `Transaction.Proofs.LegacySighash`
- **Theorems**: `evalScript_checker_extends`, `verifyScript_checker_extends`: if a checker `d` gives every answer of a checker `c`, the call with `c` is unsupported or the call with `d` gives the same result. `verifyScript_checker_congr`: two checkers that extend `c` agree when the call with `c` is decided. `transactionChecker_extends_fixedDigestChecker`: for a transaction with at most `nIn` outputs, `transactionChecker` gives every answer of `fixedDigestChecker`, a checker without a transaction. It answers only a signature check with an invalid key, an empty signature or a SINGLE hash type, and it asks `verify` about the digest `legacyOne`. `verifyLegacySpend_eq_fixedDigest`: for an `InputContext` with at most `index` outputs, when `verifyScript` with `fixedDigestChecker` is decided, `verifyLegacySpend` gives the same result. `verifyLegacySpend_fixedDigest_congr`: two such inputs with the same `scriptSig` and previous `scriptPubKey` give the same result, for any other difference of the two transactions and indices. `verifyLegacySpend_p2pkh_fixedDigest`, `verifyLegacySpend_multisig_fixedDigest`, `verifyLegacySpend_p2shMultisig_fixedDigest`: the call is decided for Pay to Public Key Hash, bare `m`-of-`n` multisig and its P2SH form, `1 ≤ m ≤ n ≤ 16`. The hypotheses: `scriptSig` is the direct pushes of the stated items, every signature satisfies `HasSingleHashType`, and `verify` decides every request on `legacyOne`. `coreVerifier` decides every request. The hypothesis of a decided call covers `OP_CHECKSIGVERIFY`, `OP_CHECKMULTISIGVERIFY` and `OP_CODESEPARATOR` in any script.
- **Comparison**: `lake test`: 44 Core-signed records of `tests/script/signed-spends/fixed-digest.jsonl` through `verifyLegacySpend` with `coreVerifier`. Verdicts and ScriptError names agree with Core's recorded results: 32 accepted and 12 rejected. `legacySignatureHash` agrees with Core's `SignatureHash` on all 142 recorded digests. On the 37 records with at most `input_index` outputs and only SINGLE hash types, `verifyScript` with `fixedDigestChecker` also gives Core's verdict. The records reuse one signature of each key in other transactions: another outpoint and sequence, another index, no outputs, another version, lock time and output, and another script code through `OP_CODESEPARATOR`. They cover `0x83`, the undefined bytes `0x23`, `0xa3` and `0xe3` without and with `STRICTENC`, both `VERIFY` opcodes, mixed hash types, and the boundary of one more output, which Core rejects. `scripts/compare_core.py` compares the 44 spends and their 71 signature hashes with live Core, with zero disagreements. `scripts/check_signed_spends.py` regenerates the records byte for byte.
- **Refinement**: None
- **Excluded**: Spends where a reached signature check has a valid key and a nonempty signature with a hash type other than SINGLE. Spends that reach the checker through CLTV or CSV. Whether a signature for `legacyOne` exists or is hard to compute. An index at or after the number of inputs, which `InputContext` excludes. Core's signature cache (D111), which DogeLib does not model. Other templates, and `n` from 17 to 20

## Script worked property, multisig with recovery

- **Definition**: `Script.multisigRecoveryScript`, `p2shScriptPubKey` in `Script.MultisigRecovery`. `OrdinaryBranch`, `RecoveryBranch`, `MultisigRecoverySpend`, `SigEncodingOk`, `KeyEncodingOk`, `sigAccepted`, `multisigVisits` in `Script.Proofs.MultisigRecovery`
- **Theorems**: For `k` of `n` keys, `1 ≤ k ≤ n ≤ 16`, under `MultisigRecoverySpend`: `multisigRecovery_sound`: acceptance implies one branch, with no stack bound and no verifier totality. `multisigRecovery_ordinary_complete`, `multisigRecovery_recovery_complete`: each branch suffices, under a stack bound on `S` and, for the ordinary branch, decided answers on the visited pairs. `multisigRecovery_accepted_iff`: the equivalence for a total verifier and `S.length + n + 1 ≤ 1000`. `multisigRecovery_twoOfThree_accepted_iff`: the same for `k = 2`, `n = 3` and `S.length ≤ 996`. `multisigRecovery_ordinary_unsupported`, `multisigRecovery_recovery_unsupported`: an undecided reached call gives `unsupported`. The ordinary theorem needs `S.length + n + 1 ≤ 1000`, and the recovery theorem needs `S.length + 2 ≤ 1000`. `multisigRecovery_lockTime_lt`: under CLTV, with the stack bound `S.length + 2 ≤ 1000`, a false selector and a lock time below 1,000,000 give `UNSATISFIED_LOCKTIME` before any signature check. `multisigRecovery_accepted_lockTime_lt`: under CLTV, with no stack bound and no verifier totality, an accepted spend with a lock time below 1,000,000 takes the ordinary branch. `multisigRecovery_lockTime_ge_threshold`, `multisigRecovery_finalSequence`: under CLTV, with the stack bound `S.length + 2 ≤ 1000`, a false selector gives `UNSATISFIED_LOCKTIME` before any signature check in two more cases. They are a lock time of at least 500,000,000, and a final sequence of the input at every lock time. `multisigRecoveryScript_twoOfThree`: the 149 bytes of section 7. `checkSignatureEncoding_ok_iff`, `checkPubKeyEncoding_ok_iff`: the predicates are Core's checks. `sigAccepted_iff`: for script code below 2^64 bytes, `sigAccepted` holds exactly when `isValidPubKey` passes and `verify` gives `some true` on the legacy digest. `MultisigRecoverySpend.sigAccepted_ordinary_iff_reference`, `sigAccepted_recovery_iff_reference`, `checkSig_ordinary_reference`, `checkSig_recovery_reference`: a checker call of either branch with a nonempty signature and a key that passes `isValidPubKey` hashes the digest of `legacyReferencePlan`. This holds for every signature list in the script code. `legacyReferencePlan` is Core's `SignatureHashOld`. `ordinaryCode_scanOps`, `recoveryCode_scanOps`: the parsed-script hypothesis holds for both branches' script code. `MultisigRecoverySpend.sigAccepted_ordinary_allOnly_commits`, `sigAccepted_recovery_allOnly_commits`: an accepted signature with an `IsAllOnly` hash type also verifies against the reference digest of every transaction with the same `legacyAllFields`. The result is invariance under equal fields: it says nothing about changed fields, and a signature-binding claim needs cryptographic and verifier assumptions. They do not say that such a transaction passes the template
- **Comparison**: `lake test`: 25 hand cases through `verifyLegacySpend` with a table verifier, a test backend. Both branches, wrong signature order, a missing signature, lock time 999,999, 1,000,000 and 500,000,000, and a final sequence. A negative-zero selector, the dummy with and without `NULLDUMMY`, CLTV clear with lock time 0, and the DER, high-S, LOW_S overflow, hash-type and key-type cases. One case checks the template bytes against section 7. 18 comparisons of `legacySignatureHash` with the `legacyReferencePlan` digest, for three template script codes and six hash types. They compare two DogeLib definitions: a consistency check, not independent evidence. `lake test` also runs all 25 Core-signed recovery-template fixtures through `verifyLegacySpend` with `coreVerifier` and their recorded flags. Both verdicts and ScriptError names agree with Core's recorded results. The three signer pairs, recovery branch and every recorded mutation are covered. A compiled sanity check checks the `multisigRecovery_sound_coreVerifier` premises for the four baselines, without constructing a proof term. `scripts/compare_core.py` compares those same 25 records with live Core through the oracle's transaction checker
- **Refinement**: None
- **Excluded**: Unforgeability, distinct signers, hash commitments beyond the supplied redeem script, chain finality. `n` from 17 to 20 (#82), which needs a data push for the key count. A production bridge instance
