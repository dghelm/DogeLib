# RIPEMD-160 and Hash160 known answers

`vectors.json` contains 31 expectations, with a source label on each record.
`lake test` checks the compiled definitions and convenience wrappers against every expectation.
It also requires nine author vectors, ten Core vectors and twelve Hash160 vectors.
It never rewrites the fixture file.

## Sources

The nine `authors` records are the published RIPEMD-160 vectors of Dobbertin, Bosselaers and Preneel.
They appear in [Bosselaers' table](https://homes.esat.kuleuven.be/~bosselae/ripemd160.html), retrieved on 2026-11-05.
The table gives ASCII messages and hexadecimal digests.
The first eight also appear in EthLib's proof file at the adaptation origin `6a93711` (SOURCES.md).
The current pin `bb6dfe5` removes those kernel known answers in `914ea4ec`.
The ninth hashes one million `a` bytes.
These numerical input/output pairs are transcribed test data, not copied implementation code or prose.

The ten `core_crypto_tests` records copy the RIPEMD-160 expectations in Dogecoin Core's `src/test/crypto_tests.cpp`, lines 204–217.
The reference software revision is `e0a1c157791544e818c901bd9341896965afbf9d` (SOURCES.md).
The final record uses `LongTestString`, defined at lines 190–200.
Each `i` from 0 through 199999 contributes five bytes: `i`, `i >> 4`, `i >> 8`, `i >> 12`, `i >> 16`.
Each byte conversion keeps the low eight bits.
These Core values retain the MIT terms in `LICENSES/dogecoin-core-MIT.txt`:

```text
Copyright (c) 2014-2016 The Bitcoin Core developers
Distributed under the MIT software license, see the accompanying
file COPYING or http://www.opensource.org/licenses/mit-license.php.
```

Core's `crypto_tests.cpp` contains no Hash160 expectations at this revision.
The twelve `hashlib_and_core_chash160` records were produced with Python 3.14.8 and OpenSSL 3.6.5 on 2026-11-05:

```python
hashlib.new("ripemd160", hashlib.sha256(message).digest()).hexdigest()
```

Every result also matched an independent executable calling Core's `CHash160().Write(data, size).Finalize(out)`.
That executable used unmodified `src/hash.h`, `src/crypto/sha256.cpp` and `src/crypto/ripemd160.cpp` from the reference software revision.
GCC 16.2.1 compiled it with `-std=c++11 -O2` on x86-64 Linux.
The build enabled the host's endian and byte-swap declarations through `HAVE_ENDIAN_H`, `HAVE_BYTESWAP_H` and their `HAVE_DECL_*` macros.
The messages include empty input, ASCII, embedded zero and high-bit bytes, all byte values, and lengths 55, 56, 63, 64, 119 and 120.

Both independent implementations agreed on all twelve digests before the fixtures were committed.
The Lean implementation did not produce any expectation.
The comparison driver is local-only and is not committed.
The committed [Core harness and comparator](../../../docs/oracle.md#the-core-harness) repeat the fixture comparison and add generated padding boundaries.

## Encoding and checksums

`hex` stores the exact input bytes in hexadecimal.
`repeat_a` stores the count `1000000`, interpreted as that many bytes of value `0x61`.
`core_long` stores an empty payload and denotes the million-byte `LongTestString` described above.
The `digest` field stores twenty bytes in digest output order, without reversal.
The `source` field identifies the expectation's producer.

The two million-byte messages are generated by the runner from these encodings.
No large message file is vendored.

`SHA256SUMS` pins `vectors.json`.
Check it from this directory with `sha256sum -c SHA256SUMS`.
A passing comparison covers these inputs only.
It proves neither cryptographic security nor equality to Core on every input.
