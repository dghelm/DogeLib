# Coverage: Blocks, Headers, and Coin Sets

This file holds the per-operation coverage detail for `Block` headers, AuxPoW, Merkle roots, header sequences, and chain work.
It also covers block subsidy, version bits, block checks, coin sets, `ConnectBlock`, and `validateBlock`.
See [COVERAGE.md](../../COVERAGE.md#operations) for the compact matrix and [COVERAGE.md](../../COVERAGE.md#legend) for field meanings and theorem tags.
See [docs/soundness/headers.md](../soundness/headers.md), [docs/soundness/blocks.md](../soundness/blocks.md), and [docs/soundness/work.md](../soundness/work.md#chain-work) for theorem hypotheses and boundaries.
See [docs/comparison-evidence.md](../comparison-evidence.md) for finite Core comparison counts, replays, and snapshot ranges.

## AuxPoW check

- **Definition**: `Block.AuxPow.check`, `searchChainRoot`, `findSubseq?`, `checkMerkleBranch`, `getExpectedIndex`, `PureBlockHeader.chainId` in `Block.AuxPowCheck`
- **Theorems**: `AuxPow.check_eq_ok_iff`: acceptance exactly when every test passes, for every payload, block hash, chain ID and `fStrictChainId`. `AuxPow.check_ok_binding`: an accepted payload has `nIndex` zero and at most 30 chain hashes. The parent's Merkle root is the left fold of the transaction ID. The script holds the reversed chain root first at an offset that meets `MarkerCondition`, then the words `2^h` and a nonce. `nChainIndex` equals the expected index. The theorem states hash equalities only, with no collision-resistance claim. `AuxPow.check_ok_chainIndex_lt`: an accepted `nChainIndex` is not negative and is below `2^h`. `searchChainRoot_eq_ok_iff`, `findSubseq?_eq_some_iff`, `findSubseq?_eq_none_iff`: first-occurrence semantics. `checkMerkleBranch_neg_one`, `checkMerkleBranch_eq_fold`, `checkMerkleBranch_zero`: the zero hash for index −1, else a left fold that takes each side from an index bit. `getExpectedIndex_eq`, `getExpectedIndex_lt` (for `h < 32`) and `getExpectedIndex_mod64` (for `h ≤ 32`)
- **Comparison**: `lake test`: the 26 deterministic cases of Core's `check_auxpow` (D56, lines 186 to 323), with bytes transcribed by an independent Python builder and each expected Boolean from its `BOOST_CHECK`. 16 boundary cases with results argued from D55 cover the branch lengths, the marker rules and the trailing words. They also cover the root in internal byte order, and negative, out-of-range and wrong-slot `nChainIndex`. Others set `fStrictChainId` false or use a negative chain ID. Each rejection is checked against the `return error` line it reaches. The six mainnet headers of the codec row are accepted with their own hash and chain ID and `fStrictChainId` true. [Provenance](../../tests/block/README.md#auxpow-check). `auxpow.check` compares all 48 verdicts with Core. The harness reconstructs all 26 `check_auxpow` inputs with Core classes and requires exact byte agreement. Seeded payload and script mutations also compare with Core ([streams](../comparison-evidence.md#header-proof-of-work-evidence)).
- **Refinement**: None
- **Excluded**: The parent's proof of work, scrypt, `CheckAuxPowProofOfWork`, the parameter record and the choice of `fStrictChainId` per network, which the *Header proof of work* row covers. Any claim that work cannot be reused across chains. A `CAuxPow` whose transaction is a default-constructed `CTransaction()` or a copy of it, with Core's cached zero hash

## Block check, `CheckBlock`

- **Definition**: `Block.checkBlock`, `CheckBlockError` with `rejectReason`, `dosScore`, `rejectCode` and `corruptionPossible`, `checkTransactions`, `legacySigOpCount` in `Block.Check`. Core's `CheckBlock` (D106) for a block with `fChecked` false, with both flags as parameters
- **Theorems**: `checkBlock_rejects_merkleDuplication` (*property*): suppose `checkBlock` accepts a block with the Merkle check. Let a second block have the same header and transaction IDs that are a `MerkleDuplication` of the first list. Then `checkBlock` rejects the second block with `duplicateTransactions`. No theorem covers the other checks or their order
- **Comparison**: `lake test`: the mainnet genesis block passes with both flags (D9, and D106 lines 1804 and 1819 to 1824). `block.check`: 2,232 requests in the full run. `scripts/compare_core.py` against Core's own function at `e0a1c15`: [evidence](../comparison-evidence.md#transaction-and-block-check-comparison-evidence). Real mainnet blocks pass with both flags. The full run has the 17 blocks at and next to the rule changes, with four mutations of each. The run with `--mainnet-blocks` has all 11,001 blocks of heights 0 to 10,000 and 6,455,302 to 6,456,301. The 1,000 recent blocks have no pinned hash ([fixtures](../../tests/block/mainnet-blocks/README.md)). Every reason of `CheckBlock` is reached
- **Refinement**: None
- **Excluded**: Testnet and regtest have no comparison. `ContextualCheckBlock` and `ConnectBlock`, which have their own rows. A block object with `fChecked` set

## Block connection, `ConnectBlock`

- **Definition**: `Block.connectBlock`, `ConnectBlockError` with `rejectReason`, `dosScore`, `rejectCode` and `isRejection`, `connectTransactions`, `connectTransaction`, `checkInputs`, `checkInputScript`, `lookupInputs`, `getValueIn`, `addFee`, `spendInputs`, `enforceBip30`, `connectScriptFlags` in `Block.Connect`. Core's `ConnectBlock` on mainnet (D114) with `CheckInputs`, for no script-check threads and no assumed-valid block. The context supplies the height, the previous hash, the hash of the ancestor at `BIP34Height` and the CSV state
- **Theorems**: `connect_fits` (*property*): `connectBlock` never returns `outOfDomain` when every output of the coin set has an amount from 0 to `MAX_MONEY` (`CoinSet.ValuesInRange`), and `spentValue` of the block plus `MAX_MONEY` and the subsidy is below `2^63` ([soundness](../soundness/blocks.md#the-coin-set-checktxinputs-and-connectblock)). `connectBlock_ne_feeNegative`, `connectBlock_ne_feeOutOfRange` (*property*): for every verifier, context, coin set and block, `connectBlock` never rejects with `bad-txns-fee-negative` or `bad-txns-fee-outofrange`. The row *Block connection, properties of an accepted block* has the theorems on the new coin set. No theorem covers the other checks or their order
- **Comparison**: `lake test`: the mainnet genesis block is accepted and adds no coin (D114, lines 1821 to 1825). `block.validate`: 42 requests in the full run, with 60 accepted and 54 rejected blocks. `scripts/compare_core.py` against Core's own `ConnectBlock` at `e0a1c15`: [evidence](../comparison-evidence.md#block-validation-comparison-evidence). Every reachable reason of design record 0010, section 5, is reached. The run with `--mainnet-blocks` replays all 10,001 blocks of heights 0 to 10,000 from the empty coin set: both programs accept every block, and the digest of each block's changes and of the whole set agree. One recorded run of `scripts/replay_blocks.py`, a gate outside CI, replays all 145,001 blocks of heights 0 to 145,000 through `blocks_file`, with the same agreement: [evidence](../comparison-evidence.md#replay-of-mainnet-to-height-145000). Stage 2 of design record 0011 recorded six ranges, A, B, C, D, F and H. They run 19,000 blocks between heights 145,001 and 5,050,000 from snapshots of the Core pass through `coins_file`. Both programs accept every block, agree on each block record and reach the digest of the pass at the end: [evidence](../comparison-evidence.md#ranges-a-to-h). Stage 4 of design record 0011 recorded two CSV-window ranges, E1 (1,198,520 to 1,200,519) and E2 (1,702,520 to 1,704,519), 4,000 blocks total. Both run from snapshots of a second Core pass with the same agreement: [evidence](../comparison-evidence.md#the-csv-window-ranges-e1-and-e2). Each range assumes that its start snapshot is Core's coin set ([soundness](../../SOUNDNESS.md#b4-the-oracle-and-foreign-boundaries))
- **Refinement**: None
- **Excluded**: Testnet and regtest. Script-check threads and assumed-valid blocks. An active CSV state and sequence locks. Core's writes after the `fJustCheck` return. A block whose sums leave the `int64_t` range. Real blocks above height 145,000 outside the eight ranges. The replay to height 145,000 is one recorded run and is not in CI. The recent range needs supplied coins and is not compared

## Block connection, properties of an accepted block

- **Definition**: `coinsBefore`, `connectChain`, `ChainLinked`, `chainSubsidy`, `coinbaseValueOut` in `Block.Proofs.ConnectProperties`. They state the theorems, and Core has no such function
- **Theorems**: `connect_spends_available` (*property*): take a block that `connectBlock` accepts, whose hash is not the genesis hash, and a transaction of it that is not a coinbase. The transaction has pairwise different outpoints. Each of its inputs has a coin in the set just before it (`coinsBefore`). No input has a coin after its spends. `connectBlock_genesis`: a block with the genesis hash leaves the set unchanged. `connect_valuesInRange` (*property*): an accepted block keeps `CoinSet.ValuesInRange`. `connect_value_bound` (*property*): on a set with `CoinSet.ValuesInRange`, an accepted block adds at most `subsidyValue` to `CoinSet.totalValue`. `connectChain_issuance_bound` (*property*): the same bound for a list of blocks with any contexts. `chain_issuance_bound` (*property*): from the empty set, a genesis-hash block and then blocks with linked contexts (`ChainLinked`) give a total value of at most `chainSubsidy`. All hold for every verifier and both values of `fJustCheck` ([soundness](../soundness/blocks.md#connect_spends_available-each-input-spends-a-present-coin))
- **Comparison**: `lake test`: on the genesis block and a hand-built block at height 1, `CoinSet.totalValue` and `chainSubsidy` are 6,841,600,000,000 koinu, Core's subsidy for height 1 (`CORE_VALUES` of `scripts/oracle_subsidy.py`). One koinu more is `bad-cb-amount`, and 5 koinu in an `OP_RETURN` output leave the total 5 below the subsidy. `scripts/compare_core.py --mainnet-blocks`: on the replay of heights 0 to 10,000, `block.validate` reports `CoinSet.totalValue` at each multiple of 1,000 and at the end. Core's harness reports the sum of its coin view at the same points, and the two are equal. Each total is at most the sum of the subsidies from height 1, which both programs give through `block.subsidy` ([oracle](../oracle.md#total-value))
- **Refinement**: None
- **Excluded**: Upper bounds only. The header checks and `ContextualCheckBlock`. Script results, maturity and amounts of the spends. Core's coin database

## Block serialization

- **Definition**: `Block.Block`, `Block.read`, `Block.decodeComplete`, `Block.encode`, `Block.baseSize`, `readTransactionsLoop` in `Block.Block`. Core's `CBlock::SerializationOp` (D108) in the witness-allowed mode and in base mode
- **Theorems**: `Block.read_encode_allowWitness` (*property*): for every block with `Block.RoundTripsAllowWitness` and all bytes `rest`, the reader returns the block from its encoding followed by `rest`, and leaves `rest`. `Block.read_encode_base` (*property*): the same in base mode under `Block.RoundTripsBase`, with the base projection as the result. `Block.baseProjection_eq`: a block is its own base projection when the AuxPoW payload transaction, if any, and every transaction of `vtx` have no witness data. No theorem says that an accepted byte string is an encoding, or which error the reader reports
- **Comparison**: `lake test`: the genesis block reads and encodes to its bytes in both modes. `tx.check` and `block.check`: 976 reader requests. They include every proper prefix of a small block, count errors, bytes after the block and both formats of a transaction. `scripts/compare_core.py` against Core's own function at `e0a1c15`: [evidence](../comparison-evidence.md#transaction-and-block-check-comparison-evidence). Both programs also read the 11,018 real mainnet blocks of *Block check*. Three of them have witness data in the parent coinbase of the AuxPoW payload.
- **Refinement**: None
- **Excluded**: A packed reader. The oracle reads a block as a byte list

## Block subsidy

- **Definition**: `Block.getDogecoinBlockSubsidy`, `generateMTRandom`, `subsidySeed`, `subsidyMaxReward`, `uniformInt`, `uniformIntAccept`, `uniformIntBucket` and `Mt19937` with `seed`, `normalizeState`, `twist`, `temper` and `next`, in `Block.Subsidy`. Core's `GetDogecoinBlockSubsidy` (D104) with the mainnet records, and Boost 1.70.0's `mt19937` and `uniform_int` (BO1 to BO3). The draw takes fuel, and `fuelExhausted` is an error that Core does not have
- **Theorems**: `uniformInt_preimages` (*property*): for `maxReward` 999,999 and 499,999, the bucket sizes are 4,294 and 8,589, and `maxReward * bucket ≤ 2^32`. A 32-bit word gives `value` exactly when `1 ≤ value ≤ maxReward` and the word lies in `[(value - 1) * bucket, value * bucket)`, so each value has exactly `bucket` words. The draw rejects a word exactly when it is at least `maxReward * bucket`. The statement is about one word, `uniformIntAccept`. `Mt19937.output_seed_10000` (*witness*): output 10,000 of the default seed 5489 is 4123659995 (S3), by kernel computation. `Mt19937.output_seed_eq` (*model agreement*): for every seed and output number `624 * q + r` with `r < 624`, the list evaluator of that computation gives the output of `seed`, `twist` and `next`. No theorem says that the draw ends, bounds a subsidy or states a distribution
- **Comparison**: `lake test`: Core's three subsidy tests (D105) through the compiled code. The chained sums are 54,894,174,438 coins for heights 0 to 100,000 and 12,349,960,000 coins for 100,000 to 145,000. Every height from 145,000 to 599,999, and 600,000 and 700,000, gives the fixed schedule. Output 10,000 of `mt19937` (S3) and the seed of the genesis hash. `block.subsidy` compares the oracle with Core's own function at the pin, built with Boost 1.70.0. The 145,166 cases have zero disagreements. 145,000 of them are the mainnet heights from 1 to 145,000 on their real previous hashes ([fixture](../../tests/block/mainnet-subsidy-prev-hashes/README.md)). The others are 54 fixed-schedule cases with hand-derived values, 35 recorded Core values and 77 boundary cases ([sets](../comparison-evidence.md#block-subsidy-comparison-evidence)). The oracle reports one redraw for 30 of the 145,000 heights. Outside CI, `scripts/compare_subsidy_seeds.py` compared all 2^28 seeds at heights 1 and 100,000, which are 536,870,912 cases, with zero disagreements and no error. The largest number of redraws is 2: 18 seeds at height 1 and 3 at height 100,000. So the 624 words of fuel suffice on every seed. The run of 2026-11-13 used the oracle of commit `c24d9b5` and took 1,641 seconds with 8 workers ([gate](../../AGENTS.md#checks), *Subsidy seeds*)
- **Refinement**: None
- **Excluded**: Testnet and regtest records. A negative height. A Boost release with another algorithm, which Core's build accepts from 1.60. `ConnectBlock`, the fees and the coinbase limit. Any claim about the distribution of subsidies

## Block validation, on the coins that a block names

- **Definition**: `CoinSet.restrict`, `CoinSet.AgreeOn`, `NamesWithin`, `NotNamed`, `SameOutcome` in `Block.Proofs.Restrict`. They state the theorems, and Core has no such function
- **Theorems**: `validateBlock_restrict` (*property*): let `keep` hold for the key of every transaction ID that a block names. On a coin set and on its restriction to `keep`, `validateBlock` returns the same error, or accepts with the same coin changes. The new sets have equal entries at the keys of `keep`. The new set of the restriction has no other entry, and the new set of the whole set keeps its old entries at the other keys. `validateBlock_agree` (*property*): the same outcome for any two sets with equal entries at the keys of `keep`. `validateBlock_frame` (*property*): an accepted block changes no entry at a key that it does not name. All hold for every verifier, both flags, every context and every coin set ([soundness](../soundness/blocks.md#validateblock_restrict-a-block-on-the-coins-that-it-names))
- **Comparison**: By execution, not by proof: `block.validate` with `coins_file` runs each block on the coins that the blocks of its request name. It gives the result of the same request with every coin in memory on 33 small requests with rejected blocks (`scripts/test_oracle.py`), on mainnet heights 9,001 to 10,000 in CI, and on heights 100,001 to 101,000 in a recorded run: [evidence](../comparison-evidence.md#ranges-from-a-snapshot)
- **Refinement**: None
- **Excluded**: A list of blocks: the theorems are about one block, and `validateBlock_agree` applies again to each next block. The oracle's reads of a snapshot and its merge of the last digest, which are `IO` code

## Block-index model

- **Definition**: `Block.IndexEntry`, `HeaderIndex`, `HeaderIndex.lookup`, `HeaderIndex.insert`, `WellFormed`, `ancestorView`, `ancestorChain`, `lastCheckpointInIndex`, `checkpointHeightsInIndex`, `genesisHash?`, `Checkpoint.blockHash?` in `Block.HeaderSequence`
- **Theorems**: Each theorem on the walk takes an index that satisfies `WellFormed`. `ancestorView_congr`: let the chain of predecessors of an entry reach height 0. Then `contextualCheckBlockHeader` gives the same result on `ancestorView` as on that whole chain. The equality holds for every network, header, adjusted time and last checkpoint. `ancestorView_congr_chain`: the same equality without the height-0 hypothesis. `ancestorWalk_valid`: every walk from an entry passes `validateWorkView`. `lastCheckpointInIndex_eq`: take an index that satisfies `WellFormed`, in which each table hash belongs to an entry at its table height. Then `lastCheckpointInIndex` equals `lastCheckpoint` on `checkpointHeightsInIndex`. `HeaderIndex.lookup_insert_self`: the lookup of an inserted hash gives the inserted entry. `lookup_insert_of_ne`: an insertion under one hash does not change the lookup of another hash
- **Comparison**: `lake test`: indexes of the five mainnet fixtures, heights 0–12, 144719–145030, 371320–371340, 1032483–1034390 and 3464739–3464760. For each of the 2276 records, the view from its entry equals the fixture records from that height down, to the depth of `contextualViewDepth_eq`. The last checkpoint is 0, 145000, 371337 or none, from D9. For 2271 candidates, the contextual check on these inputs gives the expected verdict. It is acceptance, `shortView` above an anchor or `bad-fork-prior-to-checkpoint` below the last checkpoint. An anchor at 144720 gives `nextWork missingAncestor` at the retarget 144960. [Expectations](../soundness/headers.md#the-block-index-model)
- **Refinement**: None
- **Excluded**: `AcceptBlockHeader` and `ProcessNewBlockHeaders`, which have their own rows. Chain work, which has the row *Chain work of an index entry*. Whether an index is the state that a node holds: anchors, failure flags, validity flags and the failed list are inputs. No comparison with Core

## Chain work of an index entry

- **Definition**: `Block.IndexEntry.chainWork`, set by `addToBlockIndex` in `Block.HeaderSequence`
- **Theorems**: Each target takes an index that satisfies `WellFormed`. `chainWork_add`: let the step accept a hash that the index lacks. The new entry has the chain work of its predecessor plus `blockProof` of its `nBits`, modulo 2^256. Without a predecessor, it has `blockProof` alone. `accept_genesis_insert`: when the index lacks the genesis hash and the header's `hashPrevBlock`, the genesis entry gets the chain work `blockProof` of its `nBits` ([soundness](../soundness/work.md#chain-work))
- **Comparison**: `lake test`: the chain work of every added entry of the 34 regtest cases (D83). One case wraps from 2^256 − 1 to 1 above a supplied anchor work. The mainnet genesis range from an empty index, `0x100010 * (h + 1)` at height `h`. Five sums over 300 mainnet headers from 144730, computed with Python integers. The sequence oracle and the Core harness compare every added entry's chain work, including the regtest wraparound case
- **Refinement**: None
- **Excluded**: `pindexBestHeader` and chain selection (decision 8). The chain work of supplied entries and anchors is an input, which `WellFormed` does not constrain.

## Checkpoints, last known

- **Definition**: `Block.lastCheckpoint`, `Checkpoint`, `checkpoints`, `checkpointHeights` in `Block.ContextualParams`
- **Theorems**: `lastCheckpoint_eq`: for every network, enabled flag and list of known heights, the result is `none` when checkpoints are disabled. Otherwise it is the greatest table height in the list, or `none` if the list has no table height. `lastCheckpoint_eq_some_iff`, `lastCheckpoint_eq_none_iff`: the same result as conditions. `checkpointHeights_sorted`: the heights of each table increase strictly
- **Comparison**: `lake test`: the size and end heights of each table, from D9. Ten table hashes equal the double SHA-256 of independent pure headers. They are the three genesis headers derived by hand, the recorded mainnet header at height 145000 and the six AuxPoW checkpoint blocks. 14 `lastCheckpoint` cases, worked out by hand from D67
- **Refinement**: None
- **Excluded**: The block index: which checkpoint hashes a node knows, and the `nHeight` of their entries. Check 4 of `ContextualCheckBlockHeader` itself, which *Contextual header check* covers. The choice of `fCheckpointsEnabled` by `-checkpoints`. No header comparison for the hashes at the other 33 table heights

## Coin set, total value

- **Definition**: `CoinSet.totalValue`, `TxCoins.value` in `Block.Coins`, and `entryValue` in `Block.Proofs.ConnectProperties`: the sum of the amounts of the outputs that the entries hold, in the integers. It also counts an output that `CoinSet.coin` cannot return ([soundness](../soundness/blocks.md#connect_value_bound-a-block-adds-at-most-its-subsidy)). Core has no such function in validation
- **Theorems**: `CoinSet.totalValue_empty`: the empty set is worth 0. `CoinSet.totalValue_spend`: a spend lowers the total by the amount of the coin of the outpoint, or leaves it without a coin. `CoinSet.totalValue_addTx`: a new entry adds its value less the value of the entry that it replaces. `CoinSet.coin_spend_self`, `CoinSet.coin_spend_of_ne`: after a spend the outpoint has no coin, and every other outpoint keeps its coin. `txidKey_inj`: different transaction IDs have different keys. `totalValue_spendInputs`: for pairwise different outpoints that all have coins, the spends lower the total by the amounts of those coins
- **Comparison**: `lake test`: the empty set is worth 0, and the totals of the row *Block connection, properties of an accepted block*. `scripts/compare_core.py --mainnet-blocks`: equal to the sum of the amounts of Core's coin view after heights 0 to 10,000, at each multiple of 1,000 ([oracle](../oracle.md#total-value))
- **Refinement**: None
- **Excluded**: A relation to the digest of the set. Core's `gettxoutsetinfo`

## Contextual block body, `ContextualCheckBlock`

- **Definition**: `Block.contextualCheckBlockBody`, `ContextualBodyError` with `rejectReason`, `dosScore`, `rejectCode` and `isRejection`, `isFinalTx`, `checkFinality`, `coinbaseHeightPrefix`, `Block.weight`, `Block.fullSize`, `WitnessTransaction.anyWitness` in `Block.ContextualBody`. Core's `ContextualCheckBlock` on mainnet (D110), with the candidate height and the CSV and SegWit activeness as inputs
- **Theorems**: `contextualBody_badBlkWeight_unreachable_after_checkBlock` (*property*): after `CheckBlock` accepts a block, the body does not return `bad-blk-weight`, under the hypothesis that the AuxPoW payload transaction has no witness data. That hypothesis excludes some real blocks ([soundness](../soundness/blocks.md#the-contextual-block-body)). `segwit_never_active` (*property*): on a header chain from the mainnet genesis whose headers pass `checkBlockHeader .mainnet`, the SegWit state is never active. So `bad-witness-nonce-size` and `bad-witness-merkle-match` are unreachable on such a chain. No theorem covers the finality, BIP34 or witness checks or their order
- **Comparison**: `block.contextual_check_body`: 22 requests. `scripts/compare_core.py` against Core's own `ContextualCheckBlock` at `e0a1c15`: [evidence](../comparison-evidence.md#contextual-block-body-comparison-evidence). The genesis block, mutations for each reachable reason, the BIP34 boundary 1,034,382/1,034,383, the BIP65 boundary 3,464,750/3,464,751, and version-bits cases 1 and 2. Every reachable reason is reached. `scripts/compare_core.py --mainnet-blocks` also compares 11,018 real blocks: the genesis-to-10000 range, the 1,000 most recent blocks and the 17 rule-change blocks, with the version-bits headers of `tests/block/mainnet-blocks/version-bits-headers`. All agree
- **Refinement**: None
- **Excluded**: Testnet and regtest. `ConnectBlock` and `block.validate`. The witness-commitment branch, which SegWit never reaches on a mainnet header chain whose headers pass `checkBlockHeader`. A block whose AuxPoW payload transaction has witness data is outside the `bad-blk-weight` theorem

## Contextual header check

- **Definition**: `Block.contextualCheckBlockHeader`, `contextualCheckBlockHeaderWithCheckpoints`, `contextualChecks`, `ContextualHeaderError` in `Block.ContextualCheck`
- **Theorems**: Most theorems take a view `prev :: rest` and the record at the candidate height `prev.nHeight + 1`. `contextualCheck_nil` takes the empty view, and `contextualCheck_congr_header`, `contextualCheck_adjustedTime_mono` and `contextualCheck_no_checkpoint` take every view.
