# Coverage: Proposed Revisions

This file holds the per-operation coverage detail for `Proposals.Framework`, the public proposal `RelativeLockTime`, and the two test-only framework examples (`ExampleFaultyLocktime` and `ExampleVersionVerify`).
See [COVERAGE.md](../../COVERAGE.md#proposed-revisions) for the compact tables, compatibility-level labels, and forced-CSV policy.
See [docs/soundness/proposals.md](../soundness/proposals.md) for theorem hypotheses and boundaries, [docs/soundness/oracle-and-harness.md](../soundness/oracle-and-harness.md) for proposal-oracle and forced-CSV boundaries, and [docs/comparison-evidence.md](../comparison-evidence.md#historical-impact-runs) for recorded historical impact runs.

The framework, public proposals, and test-only framework examples stay in separate sections below.
Neither example is a proposal for Dogecoin, and DogeLib takes no position on the activation of `RelativeLockTime`.

## Framework

### Framework, activation model

- **Definition**: `Proposals.Framework.Activation`, `Activation.isActive`
- **Theorems**: `Activation.isActive_iff`: active exactly at heights at or above the network's activation height. `Activation.none_inactive`: never active on a network without a height. `Activation.isActive_lt`, `isActive_of_le`, `isActive_mono`: false below the activation height and monotone above it. For every activation, network and height
- **Comparison**: None
- **Refinement**: None
- **Excluded**: Version-bit signalling (design record 0007, decision 11)

### Proposed revision `RelativeLockTime`

- **Definition**: `Proposals.RelativeLockTime`: `applicable`, `lockTimeArgs`, `csvOpcode`, `isCsvOpcode`, `withCsvFlag`, `scriptFlags`, `ConnectRejection`, `ConnectReason`, `ValidateRejection`, `ValidateReason`, `connectEmbedding`, `validateEmbedding`, `txTest`, `blockRevision`, `BlockArgs`, `baselineValidate`, `revisedValidate`, `embedBaseline`, `RunsCutoff`, `operandScript`, `RunsOpcode`, `RunsSequenceLock`. `Proposals.RelativeLockTime.SequenceLocks`: `RevisionError`, `Reason`, `InputLock`, `ancestorMedianTimePast`, `inputLock`, `calculateSequenceLocks`, `evaluateSequenceLocks`, `sequenceLocksWith`, `sequenceLocks`. The revision sets the lock-time arguments of the baseline `contextualCheckBlockBody`: `csvActive` true and `Work.medianTimePast` of the view, when `active` is true on an applicable block. A block is applicable when its view is not empty and its header does not have the genesis hash. Through extension E1, `scriptFlags` adds `SCRIPT_VERIFY_CHECKSEQUENCEVERIFY` to `connectScriptFlags` when `active` is true, as Core's `ConnectBlock` does with an active CSV state. The opcode is the baseline `checkSequenceStep`, with no second copy. The spend check is the baseline's. Through extension E2, the transaction test is `sequenceLocks`: Core's `CalculateSequenceLocks` and `EvaluateSequenceLocks` with unbounded integers, on the view of the predecessor, which `blockRevision` takes as an argument. A transaction that fails has the error `RevisionError.sequenceLocks`, Core's `bad-txns-nonfinal` of `ConnectBlock`. The test has three results outside the model, which are never rejections: `ancestorOutsideView`, `coinAboveBlock` and `heightOutOfDomain`. The outcome types are sums with the baseline values under `Sum.inl`. Sources: D110, D18, D114, D35 and D3, with P1, P2, P3 and P4
- **Theorems**: Block-level, for the three rules. `relativeLockTime_softFork`, **block-level**: the framework's `SoftFork` for `revisedValidate` and `validateBlock`, with the use predicate of each rule (`RunsCutoff`, `RunsOpcode`, `RunsSequenceLock`). It joins the inactive equality, the restriction, `relativeLockTime_strict` (three strictness witnesses, each with the error of its rule) and `relativeLockTime_use` (three use witnesses). It is about one block on a supplied coin set and view, and it is not a soft-fork claim about the network. `relativeLockTime_chain`, block-level, for connection alone: a list of blocks, each with the view of its predecessor and its context, that the revised connection accepts from a coin set is accepted by `connectChain`, to the same final set, for every activation. It covers the flag and the sequence locks, and not the cutoff. `relativeLock_enforced`, block-level: suppose that the active revision accepts an applicable block, in which an input of a transaction that is not a coinbase spends a coin whose script is a push of an operand of at most 5 bytes, then `0xb2`, then a script without `0xb2`. Let the `scriptSig` have no `0xb2`, and let the operand have bits 31 and 22 clear. Then the height of the block is at least the height of the coin plus the low 16 bits `d` of the operand. `relativeLock_enforced_time`, block-level: the time form, for an operand with bit 31 clear and bit 22 set. The median time past `t` of the ancestor of the coin and the median time past `m` of the predecessor then meet `t + 512 * d ≤ m`. `relativeLockTime_inactive_eq`: with `active` false, `validateBlockWithActive` with the revision equals the embedded result of `validateBlock`, for every context. `relativeLockTime_activation`, `relativeLockTime_activation_of_lt`, `relativeLockTime_activation_of_none`: the same for `validateBlockWith` where an activation is inactive at the height of the block. `relativeLockTime_restricts`: a block that the revision accepts, `validateBlock` accepts, with the same coin set and the same changes, for every `active` and context. The statement covers the three rules. `relativeLockTime_eq_of_not_applicable`: on a block that is not applicable, the revision equals the embedded result of `validateBlock`, for every `active`. `relativeLockTime_eq_of_untouched`: take a context with `csvActive` false, and a block in which no rule has an object. The block has no cutoff transaction. No transaction that is not a coinbase has both a version of at least 2 and an input whose sequence has bit 31 clear (`SequenceUntouched`). No `scriptSig`, spent `scriptPubKey` or P2SH redeem script of a spend holds an instruction `0xb2`. Then the revision equals the embedded result of `validateBlock`. A cutoff transaction has a time lock time from the median cutoff to below the block time, and an input that is not final. `contextualBody_eq_of_cutoff_untouched`: the body check alone needs the first condition alone. `cutoff_strict`: a made block at height 145,000 that `validateBlock` accepts and the active revision rejects with `bad-txns-nonfinal`. `cutoff_use`: a made block that the active revision accepts, on which the rule runs (`RunsCutoff`). `cutoff_softFork`: the framework's `SoftFork` for the revision and `validateBlock`, with the witnesses of the cutoff. `opcode_strict`: a made block at height 145,000 that spends a coin with the script `01 01 b2`, from a transaction of version 1. `validateBlock` accepts it, and the active revision rejects it with `UNSATISFIED_LOCKTIME`, as a failure that is not mandatory. `opcode_use`: the same block with version 2, which the active revision accepts, and on which the rule runs (`RunsOpcode`). `opcode_softFork`: the framework's `SoftFork` with those two witnesses. `sequence_strict`: a made block at height 145,000 that spends a coin at height 144,999 with the sequence 2, from a transaction of version 2. `validateBlock` accepts it, and the active revision rejects it with `RevisionError.sequenceLocks`: the height lock is one block short. `sequence_use`: the block of `opcode_use`, whose input has a met height lock of one block (`RunsSequenceLock`). `sequence_softFork`: the framework's `SoftFork` with those two witnesses. Rule-level, for one transaction on a supplied view and supplied coins: `sequenceLocks_inactive`: with `active` false, or with a version below 2 as an unsigned value, `sequenceLocks` accepts. `sequenceLocks_iff`: take `active` true, a version of at least 2 and a result that is not outside the model. Then `sequenceLocks` accepts exactly when the view is empty, or the view has a median time past `m` and each input with bit 31 clear meets its lock (`LockMet`): `c + n ≤ height` with bit 22 clear, and `t + 512 * n ≤ m` with bit 22 set. Rule-level: `medianTimePast_of_headerPassed`, `lockTimeArgs_of_headerPassed`, `lockTimeCutoff_le`: on an applicable block whose contextual header check passes, the revised cutoff is the median time past of the view, and it is below the time of the block. `scriptFlags_p2sh`, `spend_restricts`, `checkInputScriptWith_withCsvFlag`: conditions 1 and 2 of the restriction for the flag, and the equality of both script runs on an input that does not read the flag. The rule-level targets `isFinalTx_mono` and `contextualCheckBlockBody_csv_restricts` are in the row *Framework, block level*. Each theorem holds for every verifier, and none assumes a property of the verifier. None is a claim about the network, about fork choice, convergence or liveness
