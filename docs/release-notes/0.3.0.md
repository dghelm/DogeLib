# DogeLib 0.3.0

DogeLib 0.3.0 adds block connection on mainnet, the replay of mainnet ranges from coin-set snapshots, the conformance corpus and the proposed revision `RelativeLockTime`.
These notes describe what changed since [0.2.0](0.2.0.md).
[COVERAGE.md](../../COVERAGE.md#operations) gives the evidence for each operation, and [SOUNDNESS.md](../../SOUNDNESS.md#what-the-proofs-say) gives the hypotheses and limits of each claim.

## Capabilities added since 0.2.0

Each item names its layer. Each claim is in the row of its operation in [COVERAGE.md](../../COVERAGE.md#operations), or in its [proposed revisions](../../COVERAGE.md#proposed-revisions) section.

### Block connection on mainnet

Stages 0010b and 0010c of [design record 0010](../design/0010-block-validity.md):

- **The coin set and `ConnectBlock`** (#159).
  [Coin set](../coverage/blocks.md#coin-set), [`CheckTxInputs`](../coverage/blocks.md#transaction-input-checks-checktxinputs), [signature-operation cost](../coverage/blocks.md#signature-operation-cost), [`ConnectBlock`](../coverage/blocks.md#block-connection-connectblock) and [the five checks of a new block](../coverage/blocks.md#block-validation-the-five-checks-of-a-new-block) follow Core on mainnet.
  `ConnectBlock` is the case of Core with no script-check threads and a null `hashAssumeValid`.
  `validateBlock` composes the five checks in Core's order. It has no block index, and it writes nothing.
  `connect_fits` gives the arithmetic domain, under two hypotheses on the amounts ([soundness](../soundness/blocks.md#the-coin-set-checktxinputs-and-connectblock)).
  The oracle operation is `block.validate`.
- **Three properties of connection** (#172).
  `connect_spends_available` needs the hypothesis that the block's hash is not the genesis hash. Then each input of an accepted block spends a present coin, and the outpoints of one transaction are pairwise different.
  `connect_value_bound` says that, on a set with amounts in range, an accepted block adds at most its subsidy to the total value.
  `chain_issuance_bound` takes a linked chain from the mainnet genesis block that `connectBlock` accepts block by block from the empty set.
  Such a chain holds at most the sum of its subsidies ([properties](../coverage/blocks.md#block-connection-properties-of-an-accepted-block), [soundness](../soundness/blocks.md#chain_issuance_bound-a-chain-holds-at-most-the-sum-of-its-subsidies)).
- **The total value** (#175).
  `block.validate` reports the [total value](../coverage/blocks.md#coin-set-total-value) of the coin set wherever it reports the set digest. The comparison requires the total of the Core harness to be equal.
  On a replay from the genesis block, each total must be at most the sum of the subsidies up to its height ([oracle](../oracle.md#total-value)).
- **The restricted coin set** (#182).
  `validateBlock_restrict` says that `validateBlock` gives the same result on a coin set and on its restriction to the transaction IDs that the block names ([coverage](../coverage/blocks.md#block-validation-on-the-coins-that-a-block-names), [soundness](../soundness/blocks.md#validateblock_restrict-a-block-on-the-coins-that-it-names)).
  No theorem states the claim for a range of blocks.
- **Speed** (#173, #183).
  Block reading is now linear in the size of the block, and the legacy signature hash hashes a packed preimage.
  The legacy signature-operation count is linear, and the duplicate-input test is O(n log n).
  Neither pull request changes a theorem statement or an oracle response.
  After #183, `nodup_of_hasDuplicate`, `checkTransaction_ok_nodup` and `checkTransactions_ok` also depend on `Classical.choice`.

[Design record 0011](../design/0011-mainnet-ranges.md) was adopted on 2026-11-20 (#174). Its stages have this state:

- **Stage 1, done** (#182). The snapshot format `dogelib-coins/1`, and `coins_file` of `block.validate` in the oracle and in the Core harness. Range S, heights 100,001 to 101,000, agrees from a snapshot ([ranges from a snapshot](../comparison-evidence.md#ranges-from-a-snapshot)).
- **Stage 2, done** (#185, #189, #191). The Core pass, a build of the Core harness, replayed mainnet to height 6,465,793 with every checkpoint. There its `hash_serialized`, `transactions` and number of coins equal the node's `gettxoutsetinfo`. - **Stage 3, tooling only** (#194). `scripts/restrict_coins.py` and `scripts/compare_range.py` have a self-test on heights 9,001 to 9,200. The range run of this stage is deferred, as [ROADMAP.md](../../ROADMAP.md#mainnet-replay-above-height-145000) says.
- **Stage 4, done** (#192, #193). `block.validate` of the oracle walks the CSV version-bits state in the CSV window. The ranges E1 and E2 agree, and both programs report the states `DEFINED`, `STARTED` and `FAILED` ([E1 and E2](../comparison-evidence.md#the-csv-window-ranges-e1-and-e2)). `versionBitsWalk_reset` and `versionBitsStateFull_of_reset` link the walk to the full walk. No theorem shows that the adapter's boundaries are those of `chainBoundaries` ([soundness](../soundness/blocks.md#version-bits)).
- **Stage 5, implemented** (#205). The conformance corpus, below.
- **Stage 6** (#179, #195, #201). Exit conditions 1 to 3 are implemented: the block level of a proposed revision and `dogelib-proposal-oracle`. The runs of conditions 4 and 5 are recorded. Both are below.

### The conformance corpus

[docs/conformance.md](../conformance.md) defines the formats of the corpus without reference to the Lean code (#205).
A program that validates Dogecoin blocks can run the ranges and compare its results with Core's. It needs no DogeLib code, no Core build and no node.
The corpus has the short range and the ranges A to D, E1, E2, F and H.
The expected results are the results of the Core harness, and `scripts/check_range_results.py` checks a program's results against them.
The blocks and the range requests are assets of the release `conformance-corpus-2026-11-24`, and [`tests/conformance/release.json`](../../tests/conformance/release.json) gives the SHA-256 of each.

On each range, the oracle and the Core harness agree on every block record and on both digests of the restricted coins ([recorded runs](../comparison-evidence.md#the-conformance-corpus)).
The restricted coins are not the coin set of mainnet, and every block of the corpus is a block that Core accepts. So a pass shows no agreement on a rejected block.
Each result holds under the hypothesis of section 3.4 of design record 0011: the snapshot at the start is Core's coin set at its height.
CI runs the short range and range D from the released assets.
Exit condition 4 of stage 5 is prepared, not run: only the tool author ran a range.

### Proposed revisions

- **The unsupported reason** (#176). The framework takes the type of unsupported reasons as a parameter, so a proposal can add reasons of its own.
- **The block level** (#179, #181). `connectBlockWith` and `validateBlockWith` state a revision of a block, with the extensions E1 to E4 of [design record 0012](../design/0012-relative-lock-time.md) ([framework, block level](../coverage/proposals.md#framework-block-level)).
  `dogelib-proposal-oracle` answers `block.validate` and `block.contextual_check_body` with the argument `revision`. Without it, the executable writes the bytes of `dogelib-oracle` on the requests of the full comparison.
- **`RelativeLockTime`** (#177, #181, #184, #186, #187). Design record 0012 was adopted on 2026-11-20, and its stages 1 to 4 are done.
  [`RelativeLockTime`](../coverage/proposals.md#proposed-revision-relativelocktime) states the rules of BIP 113, BIP 112 and BIP 68 at one fixed activation height. It follows Core's code of each rule at the pin.
  It is the first revision with a public proposal for Dogecoin. DogeLib takes no position on the activation of these rules.
  `relativeLockTime_softFork` is its claim at the level of one block on a supplied coin set and view. It is not a claim about the network ([soundness](../soundness/proposals.md#proposed-revisions-relativelocktime)).
  The sequence locks have three results outside the model, and none is a rejection.
- **Core with the CSV state forced to `ACTIVE`** (#184, #186, #187). The Core harness can seed the CSV state, so that Core's own dormant code of each rule runs.
  The `revised` object of the proposal executable agrees with it on made blocks with hand-derived verdicts. It also agrees on 11,018 mainnet blocks through `ContextualCheckBlock` and on mainnet heights 0 to 10,000 through `block.validate` ([results](../comparison-evidence.md#core-with-the-csv-state-forced-to-active-results)).
  Agreement shows that the Lean rule equals Core's dormant code on these requests. It does not show that the rule is right for Dogecoin. This state does not occur on mainnet (`csv_never_lockedIn`).
- **Historical impact runs** (#195, #201). `RelativeLockTime` ran from height 1 on heights 0 to 145,000, and on the short range, S and the ranges of design record 0011.
  Each candidate list was committed before its runs and has 0 candidate blocks.
  No run changed a block or gave an unsupported result, so each count of design record 0012, section 10.3, is 0 on these ranges ([impact runs](../comparison-evidence.md#historical-impact-runs)).
  [`tests/proposals/impact/runs/`](../../tests/proposals/impact/runs/index.json) has one record of hashes, counts, time and memory for each run, and CI checks the records.
- **Test-only examples** (#200). `ExampleVersionVerify` and `ExampleFaultyLocktime` moved to the test-only library `ProposalExamples` under `tests/`, with the test executable `proposal-test-oracle`.
  They stay as the tests of the framework.

### Script

- **The fixed digest of `SIGHASH_SINGLE`** (#167). Core's `SignatureHash` returns a fixed digest for the hash type SINGLE when the input index is at least the number of outputs.
  The theorems of the [fixed-digest property](../coverage/script.md#script-worked-property-fixed-digest-of-sighash_single) state the consequence above the hash plan, and the comparison reuses a signature in another spend ([soundness](../soundness/script.md#script-worked-property-the-fixed-digest-of-sighash_single)).

### Fixtures

- **Headers around height 600,000** (#169). A header fixture pins the hashes of the four committed rule-change blocks at heights 599,998 to 600,001.
  The maintainer's node and two approved public Electrum servers returned the same four headers byte for byte. All three sources are untrusted, so their agreement does not establish that the headers are on mainnet.

## Breaking changes

Eight pull requests have `!` in their titles.
The oracle format stays `dogelib-oracle/1` ([format stability](../oracle.md#format-stability)).
A consumer pins a release and uses that release's oracle, harness and comparison tools.

- #175 `feat(block)!: compare the total value of the coin set with Core`.
  `block.validate` reports `set_value`, a string of decimal digits, wherever it reports `set_digest_hex`.
  The comparator requires the exact field set of a response, so an oracle or a harness from before this change fails against it.
- #176 `feat(proposals)!: parameterize the unsupported reason of the framework`.
  `StepOutcome`, `EvalOutcome` and `VerifyOutcome` take a second type parameter `υ`, and `evalScriptWith`, `verifyScriptWith`, `baselineStep` and the `ofBaseline` maps take `embedU` after `embed`.
  A proposal without its own reasons uses `υ = Unsupported` with `embedU = id`. The theorems keep their meaning and take the added map.
- #181 `feat(proposals)!: add the layer extensions and the BIP 113 cutoff`.
  `BlockRevision` has two more type parameters and three more fields, and `connectTransactionWith` and `checksBeforeConnect` take one more argument.
  `connectBlockWith_congr_spend` is now `connectBlockWith_congr_revision`, and `validateBlockWith_ok_of` is now `validateBlockWithActive_ok_of`.
  `dogelib-proposal-oracle` answers `block.contextual_check_body` with the argument `revision`.
- #184 `feat(proposals)!: add the CSV flag of BIP 112 to RelativeLockTime`.
  `relativeLockTime_eq_of_cutoff_untouched` became `relativeLockTime_eq_of_cutoff_opcode_untouched`, with one more hypothesis.
  `connectTransactionWith_congr` and `connectTransactionsWith_congr` take two flag sets that agree on `SCRIPT_VERIFY_P2SH`.
- #186 `feat(proposals)!: add the sequence locks of BIP 68 to RelativeLockTime`.
  `RelativeLockTime.blockRevision` takes the view of the predecessor as a second argument, and `revisedValidate` returns a `BlockOutcome` with a baseline rejection under `Sum.inl`.
  `relativeLockTime_eq_of_cutoff_opcode_untouched` became `relativeLockTime_eq_of_untouched`, and `connectBlockWith_eq_of_opcode_untouched` became `connectBlockWith_eq_of_untouched`, each with a new hypothesis.
- #187 `test(proposals)!: compare the sequence locks with Core's dormant code`.
  The object `forced` of a `block.validate` record of the Core harness has the field `unsupported`.
  Two kinds of forced request now get a response, where they got a request error.
  They are a request with a time lock on an ancestor outside the chain, and a request with a coin height from `2^31 - 65535`.
- #192 `feat(block)!: walk the CSV window in block.validate of the oracle`.
  A `block.validate` request whose boundary is in the CSV window now gets a result, where the oracle returned the adapter error `version_bits`/`gap`.
  Each `chain` entry can hold a `version`, and `version_bits_heights` is an argument of both programs. A request without these two arguments gets the same response as before.
- #200 `refactor(proposals)!: move the example revisions to a test-only library`.
  The argument `revision` of `dogelib-proposal-oracle` no longer names `ExampleVersionVerify` or `ExampleFaultyLocktime`, and a request that names one gets a request error.
  Use the test executable `proposal-test-oracle` for the examples.

## What a user trusts

[SOUNDNESS.md](../../SOUNDNESS.md#summary) names each risk, and its area files under `docs/soundness/` give the details (#199).
The trust policy has no new exception: `lake exe check-decls` allows only `propext`, `Classical.choice` and `Quot.sound` ([C1](../../SOUNDNESS.md#c1-the-lean-kernel-and-its-axioms)).
These checks and boundaries are new in 0.3.0:

- **Kernel replay** (#198, #206). The workflow `replay` replays each module of `DogeLib`, and of the test-only `ProposalExamples`, into Lean's kernel on each push to `main` and every week.
  Each constant that a module stores must equal the constant in the replayed environment. This closes the gap of Lean issues 16730 and 16688 for the replayed libraries.
  The replay uses the same kernel as Lean, does not replay `Refinement/`, and does not run on pull requests ([C3](../../SOUNDNESS.md#c3-declarations-the-kernel-did-not-check)).
- **The source check** (#206). `scripts/check_lean_commands.py` reports listed commands, attributes and names that can run code or write the environment, except in files that its allowlist pins by SHA-256.
  It is a review aid, not a proof that no code runs while Lean builds the libraries ([the source check](../../SOUNDNESS.md#the-source-check)).
- **The declaration check** (#197). It now finds an axiom that only a constructor of an imported inductive type carries, or only another type of the same mutual declaration.
  `Exports` no longer imports a proof module (#196).
- **Snapshots and files.** The reads of a blocks file and of a coin-set snapshot are `IO` code that no theorem covers ([B4](../../SOUNDNESS.md#b4-the-oracle-and-foreign-boundaries)).
  The evidence of each range from a snapshot holds under the hypothesis that the snapshot is Core's coin set at its height.
- **Core with the CSV state forced to `ACTIVE`.** For `RelativeLockTime` the harness seeds a state that mainnet never reaches. This evidence is not a Core comparison of the baseline.

Source review, not a theorem, connects each Lean definition to the Core code that it follows.

## Boundaries of the release

DogeLib defines no chain validity. It decides the validity of a block only against a supplied predecessor and coin set ([README.md](../../README.md#status)).
DogeLib 0.3.0 does not specify these parts of Dogecoin:

- `ConnectBlock` and `ContextualCheckBlock` on testnet and regtest, and the subsidy and coinbase maturity of testnet and regtest
- `ConnectBlock` with script-check threads, an assumed-valid block or an active CSV state, and Core's undo data and writes
- The node's clock and peer time offsets, the node's block index, chain selection, reorganization and the mempool
- The witness v0 signature hash, and witness script verification

`RelativeLockTime` is a proposed revision, not part of the baseline.
The range run of stage 3 of design record 0011 is deferred, so stage 0010b of design record 0010 stays open.
[ROADMAP.md](../../ROADMAP.md#next-work) lists the next work.
