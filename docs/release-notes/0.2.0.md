# DogeLib 0.2.0

DogeLib 0.2.0 adds contextual header validation, header sequences, proposed revisions, a bug-finding campaign and the block checks that need no coins.
These notes describe what changed since [0.1.0](0.1.0.md).
[COVERAGE.md](../../COVERAGE.md#operations) gives the evidence for each operation, and [SOUNDNESS.md](../../SOUNDNESS.md#what-the-proofs-say) gives the hypotheses and limits of each claim.

## Capabilities added since 0.1.0

Each item names its layer. Each claim is in the row of its operation in [COVERAGE.md](../../COVERAGE.md#operations):

- **Contextual header validation** ([design record 0006](../design/0006-contextual-header-validation.md)).
  Median time past, the contextual parameters by height, the last known checkpoint, and `ContextualCheckBlockHeader` on a checked view of the predecessor's chain.
  `contextualCheck_eq_ok_iff` and one theorem for each rejection give the exact result on their stated domain ([soundness](../soundness/headers.md#contextual-header-validation)).
  The oracle operation is `block.contextual_check`.
- **Header sequences** ([design record 0008](../design/0008-header-sequence-validation.md)).
  Core's `AcceptBlockHeader` and `ProcessNewBlockHeaders` over an explicit model of the block index, and `GetBlockProof` with the chain work of each entry.
  `process_linear` gives the result for headers that extend one entry in order, under its stated hypotheses ([soundness](../soundness/headers.md#the-sequence-processnewblockheaders)).
  The oracle operation is `block.header_sequence`.
- **Block checks without coins** (stage 0010a of [design record 0010](../design/0010-block-validity.md)):
  - The block codec, `CheckTransaction`, the legacy signature-operation count and `CheckBlock`.
    `checkBlock_rejects_merkleDuplication`: let `checkBlock` accept a block with the Merkle check.
    Let a second block have the same header and a `MerkleDuplication` of its transaction IDs.
    Then `checkBlock` rejects the second block with `duplicateTransactions` ([soundness](../soundness/blocks.md#block-codec-checktransaction-and-checkblock)).
  - The mainnet block subsidy, with Boost 1.70.0's `mt19937` and `uniform_int` ([soundness](../soundness/blocks.md#block-subsidy)).
  - The version-bits state on mainnet. `csv_never_lockedIn` takes a header chain from the mainnet genesis whose headers pass `checkBlockHeader`.
    On such a chain, the CSV and SegWit states are never `LOCKED_IN` or `ACTIVE` ([soundness](../soundness/blocks.md#version-bits)).
  - `ContextualCheckBlock` on mainnet. `contextualBody_badBlkWeight_unreachable_after_checkBlock` holds under the hypothesis that the AuxPoW payload transaction has no witness data.
    Under that hypothesis, after `CheckBlock` accepts a block, the body does not return `bad-blk-weight` ([soundness](../soundness/blocks.md#the-contextual-block-body)).
  - The oracle operations `tx.check`, `block.check`, `block.subsidy` and `block.contextual_check_body`.
- **Proposed revisions** ([design record 0007](../design/0007-proposed-revisions.md)).
  A framework that states a revision of the Script rules and classifies it against the baseline, for example as a `SoftFork`.
  It has two invented examples and no proposal for Dogecoin.
  Its compatibility theorems are Script-local ([soundness](../soundness/proposals.md#proposed-revisions-the-framework)).
  [docs/in-practice.md](../in-practice.md) gives worked examples, with the deliberately faulty example `ExampleFaultyLocktime`.
- **Campaign** ([design record 0009](../design/0009-bug-finding-campaign.md)).
  `scripts/campaign.py` generates spends that Core signs, checks stated properties of them, reduces a failure and replays it on a regtest node.
  It found no fault in Core or in DogeLib, and its regression fixtures come from planted faults ([campaign](../../COVERAGE.md#campaign-infrastructure)).
- **Core harness.** The harness compiles Core's `src/validation.cpp` and calls Core's own functions for `block.contextual_check`, `block.header_sequence` and the new block operations.
  `block.check_version` still compares with a transcription of two branches of Core's source.
- **Model reads.** [docs/reviews/](../reviews/README.md) records ten reads of the definitions against Core's source by an AI model.
  A read executes nothing, and it is not a review by a person.

## Comparison evidence

A full comparison with Core `e0a1c15` sends 389,628 stream requests, and it passes only with zero failures ([counts](../comparison-evidence.md#the-comparison)).
The comparator also fails if the number of requests for any operation differs from its table.

`block.check` and `block.contextual_check_body` agree with Core on 11,018 real mainnet blocks ([evidence](../comparison-evidence.md#transaction-and-block-check-comparison-evidence)).
They are heights 0 to 10,000, the 1,000 blocks from 6,455,302, and 17 blocks at and next to the rule changes.
The full comparison has the 17 rule-change blocks, and a separate run with `--mainnet-blocks` has the two ranges.
The blocks of the two ranges are release assets that the comparison checks by SHA-256 ([D3](../../SOUNDNESS.md#d3-wrong-fixtures)).

Two runs outside CI add evidence ([checks](../../AGENTS.md#checks)):

- *Subsidy seeds* compared `block.subsidy` with Core on all 2^28 seeds at heights 1 and 100,000, with zero disagreements and no error.
- *Version-bits walk* compared the version-bits state with Core's `VersionBitsState` on the real mainnet header chain through the CSV window.
  The two agreed at each of the 11 period boundaries that the run compared.

A comparison covers its requests and no other inputs.

## Breaking changes

One pull request has `!` in its title:

- #143 `test(harness)!: call Core's validation functions in the comparison`.
  The request and response shapes do not change.
  Two behaviours of the harness change.
  The harness visits Core's failed-block list in address order, where the transcription used request order.
  That order can change only `marked_failed_child`, and only when two failed members are ancestors of one predecessor. The comparator already excludes the field in that case.
  The harness also no longer writes Core's log messages to standard error.
  The harness build now needs libevent's development files, and it downloads and builds Boost 1.70.0.

The oracle format stays `dogelib-oracle/1` ([format stability](../oracle.md#format-stability)).

## What a user trusts

[SOUNDNESS.md](../../SOUNDNESS.md#summary) names each risk.
The trust policy has no new exception: `lake exe check-decls` allows only `propext`, `Classical.choice` and `Quot.sound` ([C1](../../SOUNDNESS.md#c1-the-lean-kernel-and-its-axioms)).
These trust boundaries are new in 0.2.0:

- **Boost.** The subsidy follows Boost 1.70.0. A Core built with a Boost release that draws in another way can pay other subsidies, and no claim covers it ([block subsidy](../soundness/blocks.md#block-subsidy)).
- **The Core harness.** For `block.contextual_check` and `block.header_sequence`, it runs Core's functions on a block index that it builds in memory ([A1](../../SOUNDNESS.md#a1-a-wrong-definition)).
  At a boundary whose median time is at or after the CSV timeout, it installs the version-bits state `FAILED` for CSV and SegWit ([the contextual block body](../soundness/blocks.md#the-contextual-block-body)).
- **Supplied context.** The adjusted time, the last known checkpoint and the block index are inputs. No theorem says that the anchors, flags and failed list of an index are the state that a node holds ([contextual header validation](../soundness/headers.md#contextual-header-validation), [the block-index model](../soundness/headers.md#the-block-index-model)).

Source review, not a theorem, connects each Lean definition to the Core code that it follows.

## Boundaries of the release

DogeLib 0.2.0 does not specify these parts of Dogecoin:

- `ConnectBlock`, the coin set, value accounting and fees, and the Script flags of each height
- `ContextualCheckBlock`, the subsidy and the version-bits state on testnet and regtest
- The sources of the inputs of the contextual header check: the node's clock and peer offsets, its block index and its choice of chain
- The witness v0 signature hash, and witness script verification
- Chain selection, reorganization and the mempool

So DogeLib cannot decide whether a block is valid.
Stages 0010b and 0010c of design record 0010, block connection and its properties, are not part of this release.
[ROADMAP.md](../../ROADMAP.md#next-work) lists the next work.
