This file is the single source registry ([CONTRIBUTING.md](CONTRIBUTING.md#sources-of-truth)). Module references and fixtures cite these pins. A pin change requires a review of the affected definitions, fixtures, and coverage claims in the same change or an explicitly linked series.

The maintainer authorized the verified-garbage source pin and BSD-3-Clause election on 2026-11-06.
Binary distributions containing this material must include its licence and notice.

The EthLib pin advances from `6a93711` to `bb6dfe5` with Lean `v4.35.0` unchanged.
The maintainer authorized this single pin change on 2026-11-06.
The revision includes ECDSA signing as a reference for later work, without adding it to DogeLib.
Its HMAC-SHA-256 files are adapted in `Cryptography.Hash.Hmac` and `Cryptography.Proofs.Hash.Hmac`.

The declaration check includes `10bc74ba`, which recognizes recursive formatting functions.
The writing checker includes selected parsing fixes from `ad1185d6`, with DogeLib's rules and vocabulary retained.
SHA-256 documentation includes the length bound and shared round constants clarified in `35f58834`.

SHA-256 and its SHA-1 adaptations retain their provenance at `6a93711`.
The current pin restructures SHA-256 in `d59f0e3a`, which DogeLib has not ported because it changes public representations and theorem statements.
RIPEMD-160 also retains its provenance at `6a93711`.
The current pin adds bounds hypotheses in `4f798a14`, which DogeLib has not ported because they change public helper contracts.

The older revisions identify adaptation origins, not additional reference pins.
The follow-up work is listed in [ROADMAP.md](ROADMAP.md#deferred-work).
DogeLib retains its kernel known answers and its writing policy instead of the upstream test-placement and policy rewrites.
Frozen design records keep their original citations.

*Proposed* means recorded in the design records and not yet built against. A pin becomes *Adopted* when a merged lane builds or compares against it.

The tool pins identify commits, with the Charon revision selected by Aeneas's `charon-pin`.
The optional Lake package under `Refinement/` builds against both pins.
The maintainer decided two questions when approving the pins on 2026-11-04:

- **Mathlib.** The Aeneas Lean library requires Mathlib `v4.35.0` (commit `56a005855ea17e0b0958f73ec801ae140b0a1679` in its `lake-manifest.json`). It enters only the separate Lake package under `Refinement/`, never the root DogeLib package (issue #3).
- **Trust policy.** The Aeneas Lean library declares seven axioms. Five declare types for Rust items it does not model, such as `core.pin.Pin`, and one in a test module declares a function. The seventh, `core.slice.Slice.get_unchecked_SliceIndexUsizeSlice_spec` (`Aeneas/Std/Slice.lean:615`), states a property. `lake exe check-decls` reports a declaration whose proof depends on any of them. A refinement proof that avoids them needs no exception. The Aeneas library also uses `native_decide` and `bv_decide`, in tests and in tactics that a proof can avoid. Decided: no exception to the trust policy. A refinement proof must not depend on these axioms.

The maintainer confirmed the Dogecoin pin on 2026-11-03 (issue #5). `v1.14.9` was then the latest Dogecoin Core release. The Dogecoin pin is a compatibility target for the operations DogeLib models. It is not a claim that every rule in that version is formalized, or that one version is enough evidence for historical consensus.

Keep these concepts separate:

- **Reference software revision:** the exact source used to investigate an operation.
- **Protocol context:** the network, branch, activation state, and historical era in which a rule applies.
- **Implemented coverage:** the operations and input domains actually modeled.
- **Proposed revision:** behavior intentionally different from the baseline.

## Known differences

Differences between DogeLib's targets and related upstream definitions. DogeLib expects these differences and handles them by design.

| Subject | Difference | Handling |
| --- | --- | --- |
| CompactSize decoding | btc-verified accepts every canonical `UInt64`. Core `v1.14.9` also rejects values above `MAX_SIZE = 0x02000000`. Input `fe 01 00 00 02` separates them. | Separate bounded reader `CompactSize.decodeBounded`, next to the generic `CompactSize.decode`. `decodeBounded_eq_ok_iff_decode` states the difference, and `decode_maxSize_succ` and `decodeBounded_maxSize_succ` the input. |
| Counted-list decoding | btc-verified reads the count with the generic CompactSize decoder, so it accepts every canonical count and then tries to read that many elements. Core `v1.14.9` rejects a count above `MAX_SIZE = 0x02000000` before it reads any element. | Separate bounded reader `CountedList.decodeBounded`, next to the generic `CountedList.decode`. `decodeBounded_eq_ok_iff` states the difference, and `decodeBoundedBytes_maxSize_succ` and `decode_maxSize_succ` the input `fe 01 00 00 02`. |
| Public-key encodings | EthLib accepts compressed and uncompressed keys. Dogecoin's bundled parser also handles hybrid encodings under applicable checks. | Review acceptance wrappers independently (D5, E6) |
| Transaction dispatch | btc-verified's top-level `Tx` models Bitcoin's witness-aware dispatch. | Adapted from the `TxBody` components, not `Tx`. `Transaction.readBase` reads an empty input list as such. `Transaction.readAllowWitness` is DogeLib's, written from D4, and models the format only. |
