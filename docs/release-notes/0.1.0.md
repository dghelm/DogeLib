# DogeLib 0.1.0

DogeLib 0.1.0 is the first release of DogeLib, an executable formal specification and proof library for Dogecoin in Lean 4.
These notes describe the capabilities on `main` at the release commit, what a user trusts, and what the release does not specify.
[COVERAGE.md](../../COVERAGE.md#operations) gives the evidence for each operation, and [SOUNDNESS.md](../../SOUNDNESS.md#what-the-proofs-say) gives the hypotheses and limits of each claim.

## Capabilities

Each item names its layer. Each claim is in the row of its operation in [COVERAGE.md](../../COVERAGE.md#operations):

- **Serialization.** Fixed-width integer, byte-string and CompactSize codecs with round trips, adapted from btc-verified.
  Core's bounded CompactSize and counted-list readers, with soundness and completeness against a separate relation.
  Packed forms of the codecs, with refinement theorems.
- **Transactions.** Transaction types, base codecs, Core's base-mode reader, the transaction ID, and the witness-allowed format as a serialization format only, with the witness hash.
- **Legacy signature hash.** The hash plan for `SIGVERSION_BASE`.
  `legacySignatureHashPlan_eq_reference` proves it equal to Core's `SignatureHashOld` transformation, for fully parsed script code and fewer than 2^32 inputs and outputs.
- **Hashes.** SHA-256 and double SHA-256 from EthLib, SHA-1, RIPEMD-160 and Hash160.
  HMAC-SHA-256 and PBKDF2-HMAC-SHA-256, each proved equal to a separate list model.
- **Work.** The DigiShield retarget, next-work selection on a checked finite view, compact-target encoding and the check of a supplied hash against a target.
  The 256-bit word paths of the retarget have arithmetic equivalence proofs.
- **Blocks and header proof of work.** 80-byte pure headers, transaction Merkle roots, full headers with the AuxPoW payload, and `CAuxPow::check`.
  Dogecoin's scrypt digest, which `powHash_eq_spec` proves equal to the RFC 7914 model on every 80-byte input.
  `CheckAuxPowProofOfWork`, `CheckBlockHeader` with `fCheckPOW` true, and the two version gates of `ContextualCheckBlockHeader`.
- **Signatures.** The secp256k1 curve and ECDSA verification, adapted from EthLib.
  Core's public-key parser, and `Script.coreVerifier`, which is Core's `CPubKey::Verify` on a 64-bit build.
- **Script.** One `EvalScript` call, `VerifyScript` with P2SH, the lock-time opcodes, and `verifyLegacySpend` for one transaction input.
  The signature checker is a parameter, and `transactionChecker` with `coreVerifier` verifies legacy signatures.
  `multisigRecovery_sound` and its two converses characterize acceptance of the multisig-with-recovery template for `k` of `n` keys with `1 ≤ k ≤ n ≤ 16`.
- **Rust refinement.** `decode_refines` proves that the Lean model extracted from a Rust CompactSize reader agrees with the bounded reader on every Rust-representable slice.
- **Oracle and Core comparison.** `dogelib-oracle` runs the specification on JSON Lines requests.
  A harness runs the pinned Core code on the same requests, and `scripts/compare_core.py` compares the two.

## What is proved and what is compared

A Lean theorem covers every input of its stated domain.
A known answer or a comparison covers only its recorded inputs.
The release has both kinds of evidence, and COVERAGE.md keeps them in separate columns.

`lake test` runs known answers through the compiled code.
Their sources include NIST CAVP, RFC 4231, RFC 7914, Wycheproof, Core's test files and Core-signed spends.

The comparison with Core `e0a1c15` processed 382,680 stream requests with zero failures ([counts](../oracle.md#the-comparison)).
That count includes requests with an unsupported Lean result and 12 checked harness refusals.
The comparator counts these requests separately, as neither agreement nor disagreement.
[The header evidence](../oracle.md#header-proof-of-work-evidence) records the header proof-of-work streams.

Some claims rest on comparison only:

- No theorem proves that `Point.mulAdd` computes Core's `secp256k1_ecmult` result. The 598 public-key inputs and the Script and transaction streams are finite evidence for that step.
- No theorem equates `Ripemd160.hash` with a separate model of RIPEMD-160.
- Source review, not a theorem, connects each Lean definition to the Core code that it follows.

## Trust boundaries

[SOUNDNESS.md](../../SOUNDNESS.md#summary) names each risk. In summary:

- **Axioms.** `lake exe check-decls` allows only `propext`, `Classical.choice` and `Quot.sound` for the safe declarations of the `DogeLib`, `Proofs` and `Refinement` libraries ([C1](../../SOUNDNESS.md#c1-the-lean-kernel-and-its-axioms)).
  A refinement proof does not depend on the axioms that the Aeneas library declares.
- **Tactics.** No theorem uses `native_decide`, `bv_decide` or `decide +native` ([C2](../../SOUNDNESS.md#c2-tactics-that-trust-compiled-code)).
- **Compiler substitutions.** These libraries have no `@[extern]`, `@[implemented_by]` or `@[csimp]` declarations ([B5](../../SOUNDNESS.md#b5-compiler-substitutions-in-this-repository)).
  ECDSA verification runs in Lean, with no call to libsecp256k1.
- **Compiled code.** The Lean compiler, the C compiler, the Lean runtime and Lean core's implementations remain trusted ([B1](../../SOUNDNESS.md#b1-the-compilers-and-the-runtime), [B2](../../SOUNDNESS.md#b2-lean-cores-own-implementations)).
- **The oracle adapter.** No theorem covers its JSON and hexadecimal conversions ([B4](../../SOUNDNESS.md#b4-the-oracle-and-foreign-boundaries)).
- **Extraction.** Charon, Aeneas, its library models, the Rust compiler and the Rust runtime remain trusted ([B6](../../SOUNDNESS.md#b6-extraction-and-the-rust-toolchain)).
- **Cryptography.** No theorem states collision resistance, unforgeability or constant-time behaviour.

## Oracle format

The oracle supports one record format, `dogelib-oracle/1`.
Before 0.1.0, the oracle, the Core harness, the fixtures and the comparator evolved together, with no compatibility promise to earlier development commits ([format stability](../oracle.md#format-stability)).
Development formats `/2` to `/6` preceded the reset to `/1`, and the oracle does not support them.
At and after 0.1.0, the maintainer sets the compatibility policy for outside consumers.

## Known limitations

DogeLib 0.1.0 does not specify these parts of Dogecoin:

- The contextual checks of a header against chain history, except the two version gates (for example `nBits` against the expected work, the checkpoints and the time checks)
- Block validity, `CheckBlock`, and transaction validity outside one input's Script verification
- The witness v0 signature hash, and witness script verification
- Full-node validation: the UTXO set, chain selection and the mempool

Other limits of the release:

- `checkBlockHeader` and `checkVersion` take the network and the parameter record as arguments. DogeLib does not model the selection of `Params()`.
- A header proof-of-work comparison with Core assumes three things about the build. They are a little-endian host without padding between header fields, an arithmetic right shift and Core's generic scrypt variant.
- `coreVerifier` follows a 64-bit build of Core. A 32-bit build can differ only on a signature of at least 2^24 bytes.

[ROADMAP.md](../../ROADMAP.md#next-work) lists candidate work after the release.
